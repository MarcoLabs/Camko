# Camko

**Camko** is a CMake build system wrapper and project manager for C++. It reads a simple `camko.toml` file, generates the underlying `CMakeLists.txt` for you, and drives CMake so you don't have to hand-write build scripts for every project.

- Configure your project once in `camko.toml`
- Let camko generate and maintain the CMake build in `.camko/`
- Build, run, and test through a small predictable CLI

> camko targets C++23 and assumes a standard `src/` / `include/` / `tests/` project layout.

# Installation

Build camko from source

```bash
git clone https://github.com/MarcoLabs/Camko.git
cd camko
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Then place the resulting `camko` binary somewhere on your `PATH`.

**Linux:**

```bash
sudo cp build/camko /usr/local/bin
```

Or, without `sudo`, install it to a user-owned directory and add the directory to your `PATH`:

```bash
mkdir -p ~/.local/bin
cp build/camko ~/.local/bin/
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc   # or ~/.zshrc
source ~/.bashrc
```

**Windows:**

1. Copy `camko.exe` (from `build\` or `build\Release\`, depending on your generator) to a permament folder, e.g. `C:\Tools\camko\`.
2. Add that folder to your `PATH`:
	- Search **"Edit the system environment variables"** in the Start menu and open it.
	- Click **Environment Variables...**
	- Under **User variables** (or **System variables** to apply it for all users), select `Path` and click **Edit...**
	- Click **New** and add `C:\Tools\camko\`.
	- Click OK on all dialogs.
3. Open a new terminal (PowerShell or cmd) and confirm it's picked up:
```powershell
	camko init test-project
```

**Requirements:**
- CMake 3.20+
- A C++ compiler and build tooling capable of building camko itself
- [Ninja](https://ninja-build.org/) - the default build system camko uses (see [`build-system`](#build)). Ninja is a separate program and is **not** bundled with CMake, so it must be installed and available on your `PATH` unless you configure a different `build-system` in `camko.toml`. It can be installed through most package managers:

```bash
sudo apt install ninja-build     # Debian / Ubuntu
sudo dnf install ninja-build     # Fedora
sudo pacman -S ninja             # Arch
brew install ninja               # macOS (Homebrew)
winget install Ninja-build.Ninja # Windows
```

- (Optional) `ccache` for faster rebuilds

> Note: `cpp-version` in `camko.toml` is configurable per-project - it's not a fixed requirement of camko itself, just the default target standard for new projects.

## Quick start

```bash
# Create a new project in ./my-app
camko init my-app
cd my-app

# Build it. This can be omitted since `camko run` builds before executing the program
camko build 

# Run it (arguments after `run` are passed through to your program's argv)
camko run argument1 argument2

# Run the test suite
camko test
```

## Project structure

A project managed by camko looks like this:

```
my-app/
├── camko.toml          # camko project configuration
├── src/                 # source files (.cpp)
├── include/             # header files (.h)
├── tests/               # test files (*_test.cpp), if enabled
├── examples/            # example programs (each with a main.cpp), if enabled
└── .camko/              # generated CMake project and build output — internal, do not edit by hand
		├── CMakeLists.txt
		└── build/           # build output, one subdirectory per build system (e.g. .camko/build/Ninja)
```

`.camko/` is always a direct child of the object root. Everything in it is generated by camko from `camko.toml` and is safe to delete - it will be generated on the next build.

Build output lives inside `.camko/build/` on purpose: it is an internal implementation detail of camko, not something you are meant to browse or modify, so it is kept out of your project's top level. Deleting `.camko/` also removes the build output and CMake cache, forcing a full rebuild.

## Commands

Every command accepts a `-h` / `--help` flag, which prints the same help text as running `camko help [COMMAND]` and exits without doing anything else (e.g. `camko build --help` shows build's help instead of generating or compiling anything).

### `camko init`

```
camko init [directory]
```

Scaffolds a new camko project.

- `directory` - where to create the project. Default to `.` (the current directory).

This creates the standard project layout (`src/`, `include/`, `camko.toml`, and a starter `main.cpp`).

### `camko build`

```
camko build
```

Generates `.camko/CMakeLists.txt` from `camko.toml` and invokes CMake to compile the project, using the build system set by `build-system` in `[build]` (Ninja by default). No flags are currently suppored - build behavior is controlled entirely through `camko.toml`

### `camko run`

```
camko run [args...]
```

Builds the project (equivalent to `camko build`) and then runs the resulting executable. Whether anything actually needs recompiling is left entirely up to CMake's own incremental build logic - camko does not do its own caching.

Any arguments after `run` are forwarded directly to your program's `main(argc, argv)`.

### `camko test`

```
camko test
```

Builds the project and then runs the test suite.

> **Note:** `camko test` currently attempts to build and run tests regardless of the `[tests].enable-tests` setting in `camko.toml` - it does not check that flag before running. If your `tests/` directory is missing, empty, or doesn't define any `*_test.cpp` files, expect the underlying CMake/CTest step to fail or report no tests found rather than being skipped cleanly.

- Test files must use the **`_test.cpp` postfix** (e.g. `foo_test.cpp`) to be picked up and registered as tests. Files that don't follow this naming convention are not included in the test build.
- Tests are only supported through **Google Test**. This is the sole testing framework camko integrates with, and it's a fixed part of the tool - it isn't configurable and there are no plans to support alternative test frameworks.

### `camko examples`

```
camko examples
```

Builds and runs every example in the project's examples directory, as set by `[examples].examples-directory`.

> **Note:** Examples are **disabled by default**. To use them, add an `[examples]` table to `camko.toml` and set `enable-examples = true` - see [`[examples]`](#examples).

- Each example is a subfolder containing its own `main.cpp` — this is what camko looks for to identify something as a runnable example. A folder without a `main.cpp` is not picked up.
- Folders can be **nested** — `camko examples` walks the tree recursively, so you can organize examples into subcategories (e.g. `examples/networking/tcp/main.cpp`, `examples/networking/udp/main.cpp`) and they'll still be discovered.
- Before running each one, camko prints which example is about to execute, so output from different examples doesn't blur together:

```
Running tcp_example
Running udp_example
```

- Examples are run in sequence, one at a time — if one blocks on input or hangs, subsequent examples won't start until it finishes or is killed.

### `camko --regenerate-config`

```
camko --regenerate-config
```

Resets `camko.toml` back to the default minimal configuration (the same one `camko init` generates — see [Minimal `camko.toml`](#minimal-configtoml)).

- If `camko.toml` already exists at the project root, it is **overwritten in place** with the default minimal config. Any customizations you made — build options, `[tests]` settings, `[examples]` settings, `[[dependencies]]` entries, etc. — are discarded.
- If `camko.toml` doesn't exist, it is created fresh at the project root with the same default contents.
- This is a standalone flag, not tied to a specific subcommand — it doesn't build, run, or touch `.camko/`. It only writes `camko.toml`.
- Useful when a config has been hand-edited into an invalid or confusing state and you'd rather start over than fix it field by field.

> **Warning:** This overwrites `camko.toml` unconditionally and does not prompt for confirmation or create a backup. If you want to keep your current settings, copy `camko.toml` elsewhere first.

### `camko help`

```
camko help [command]
```

Prints general help, or detailed help for a specific command.

- `command` - the subcommand to show help for (`init`, `build`, `run`, `test`, or `examples`). Optional; if omitted, camko prints its general help/usage summary.
- Running `camko help [command]` shows the same text as running that command with `-h` or `--help`.
- Passing an unrecognized command name reports an error and points you back to `camko help [COMMAND]`.

```bash
camko help
camko help build
```

## Configuration reference (`camko.toml`)

### [project]

| Key       | Type   | Description                          |
|-----------|--------|---------------------------------------|
| `name`    | string | Name of the project / executable.    |
| `version` | string | Project version (e.g. `"0.1.0"`).    |
 
```toml
[project]
name = "main"
version = "0.1.0"
```
 
### `[build]`
 
| Key                  | Type    | Default   | Description |
|----------------------|---------|-----------|-------------|
| `type`               | string  | `"Debug"` | CMake build type: `Debug`, `Release`, `RelWithDebInfo`, or `MinSizeRel`. |
| `cpp-version`        | integer | `23`      | C++ standard to compile against. |
| `source-directory`   | string  | `"src"`   | Directory containing `.cpp` source files. |
| `header-directory`   | string  | `"include"` | Directory containing header files. |
| `build-system`       | string  | `"Ninja"` | Build system (CMake generator) used to build the project, e.g. `"Ninja"` or `"Unix Makefiles"`. **Case-sensitive.** See [Choosing a build system](#choosing-a-build-system). |
| `build-shared-libs`  | bool    | `false`   | Build libraries as shared (`.so`/`.dll`) instead of static. |
| `enable-warnings`    | bool    | `true`    | Enable compiler warnings. |
| `warnings-as-errors` | bool    | `false`   | Treat warnings as build errors. |
| `enable-sanitizers`  | bool    | `false`   | Build with AddressSanitizer/UndefinedBehaviorSanitizer enabled. |
| `enable-lto`         | bool    | `false`   | Enable link-time optimization. |
| `enable-ccache`      | bool    | `true`    | Use `ccache` for compilation when it's available on the system. |
 
```toml
[build]
type = "Debug"
cpp-version = 23
source-directory = "src"
header-directory = "include"
build-system = "Ninja"
build-shared-libs = false
enable-warnings = true
warnings-as-errors = false
enable-sanitizers = false
enable-lto = false
enable-ccache = true
```

#### Choosing a build system

The optional `build-system` key in `[build]` selects which build system CMake generates files for and drives. If it is omitted, camko uses **Ninja**.

```toml
[build]
build-system = "Unix Makefiles"
```

- The value must be the name of a CMake generator available on your machine (run `cmake --help` to see the list under "Generators").
- The value is **case-sensitive**. `"Ninja"` works, but `"ninja"` does not. The same applies to every other generator name (e.g. `"Unix Makefiles"`, not `"unix makefiles"`).
- Ninja is the default, but it is not bundled with CMake. Install it separately (see [Requirements](#installation)) or set `build-system` to a generator you already have.
- Whichever build system you pick has to be installed and on your `PATH`; camko does not install it for you.
- Each build system gets its own build directory inside `.camko/build/`, named after the value of `build-system`: `.camko/build/Ninja` for `"Ninja"`, `.camko/build/Unix Makefiles` for `"Unix Makefiles"`, and so on. Note the directory name keeps the generator's exact spelling, spaces included.
- Changing `build-system` **discards all previous caches**. When you switch to a different build system, the CMake caches and build output of the previous build systems are thrown away, and the project is built from scratch with the new one. Expect a full rebuild after every change, including when you switch back to a build system you used before - nothing is kept from earlier builds.
 
### `[tests]`
 
| Key               | Type   | Default     | Description |
|-------------------|--------|-------------|-------------|
| `enable-tests`    | bool   | `false`     | Enable building and registering tests. |
| `tests-directory` | string | `"tests"`   | Directory containing test files. Files must follow the `*_test.cpp` naming convention. |

> Tests are built with **Google Test** - this is the only supported testing framework and is not configurable. Only files ending in `_test.cpp` inside `tests-directory` are picked up. Note that `camko test` (see [Commands](#camko-test)) does not currently check `enable-tests` before attempting to run tests.
 
```toml
[tests]
enable-tests = false
tests-directory = "tests"
```

### `[examples]`

The `[examples]` table is entirely optional. If it is omitted, examples are **disabled**.

| Key                  | Type   | Default | Description |
|----------------------|--------|---------|-------------|
| `enable-examples`    | bool   | `false` | Enable building and running examples. Must be a boolean - any other type is a config error. |
| `examples-directory` | string | —       | Directory containing the examples. **Required when `enable-examples = true`**; ignored otherwise. |

- Examples are **disabled by default**. The table can exist without `enable-examples`, in which case examples stay disabled.
- If `enable-examples` is present but is not a boolean, camko reports an error instead of falling back to the default.
- If `enable-examples = true` and `examples-directory` is missing or is not a string, camko reports an error. There is no implicit fallback to `"examples"` once examples are enabled, so always set the directory explicitly.
- When `enable-examples = false`, `examples-directory` is not read or validated.
- Each example is a subfolder of `examples-directory` containing its own `main.cpp`; nested folders are discovered recursively. See [`camko examples`](#camko-examples).

```toml
[examples]
enable-examples = true
examples-directory = "examples"
```
 
### `[[dependencies]]`
 
Dependencies are declared as an array of tables and are fetched via CMake's `FetchContent`. Each entry pulls a dependency straight from a Git repository at a given tag/commit — there's no separate lock file or package manager involved.
 
| Key                 | Type   | Required | Description |
|---------------------|--------|----------|-------------|
| `name`              | string | yes      | A label for the dependency (used internally by `FetchContent`). |
| `repo`              | string | yes      | Git URL of the dependency's repository. |
| `version`           | string | yes      | Git tag, branch, or commit SHA to fetch. Pinning to a commit SHA is recommended for reproducible builds. |
| `link-target`       | string | no       | The CMake target to link against, e.g. `fmt::fmt`. If omitted, defaults to `[name]::[name]`. |
| `find-package-name` | string | no       | The name to use when the dependency is resolved via `find_package` instead of being fetched (e.g. when it's already installed via a system package manager). Only needed in that case. |
 
```toml
[[dependencies]]
name = "fmt"
repo = "https://github.com/fmtlib/fmt.git"
version = "10.2.1"
link-target = "fmt::fmt" # if omitted, automatically becomes [name]::[name]
 
[[dependencies]]
name = "json"
repo = "https://github.com/nlohmann/json.git"
version = "v3.11.3"
link-target = "nlohmann_json::nlohmann_json"
find-package-name = "nlohmann_json" # only needed if installed using a package manager
```
 
> **Note:** A library's `FetchContent` name and its actual CMake link target are two different things. If you're not sure what target a dependency exports, check its README, look for `add_library`/`ALIAS` definitions in its `CMakeLists.txt`, or run `cmake --build build --target help` after fetching it.

## Minimal `camko.toml`
 
Everything under `[build]` besides `type`, `cpp-version`, `source-directory`, and `header-directory` is optional and will fall back to its default (including `build-system`, which defaults to `"Ninja"`). `[tests]`, `[examples]` and `[[dependencies]]` are entirely optional. This is the minimal config `camko init` generates for a new project, and what `camko --regenerate-config` writes back out:
 
```toml
[project]
name = "main"
version = "0.1.0"
 
[build]
type = "Debug" # Debug | Release | RelWithDebInfo | MinSizeRel
cpp-version = 23
source-directory = "src"
header-directory = "include"
```
 
## Full example `camko.toml`
 
```toml
[project]
name = "main"
version = "0.1.0"
 
[build]
type = "Debug" # Debug | Release | RelWithDebInfo | MinSizeRel
cpp-version = 23
source-directory = "src"
header-directory = "include"
build-system = "Ninja"     # CMake generator name, case-sensitive ("ninja" won't work)
build-shared-libs = false
enable-warnings = true
warnings-as-errors = false
enable-sanitizers = false  # Build with ASan/UBSan enabled
enable-lto = false         # Enable link-time optimization
enable-ccache = true       # Enable ccache when available
 
[tests]
enable-tests = false
tests-directory = "tests"

[examples]
enable-examples = false      # disabled by default
examples-directory = "examples" # required when enable-examples = true
 
[[dependencies]]
name = "fmt"
repo = "https://github.com/fmtlib/fmt.git"
version = "10.2.1"
link-target = "fmt::fmt" # if omitted, automatically becomes [name]::[name]
 
[[dependencies]]
name = "json"
repo = "https://github.com/nlohmann/json.git"
version = "v3.11.3"
link-target = "nlohmann_json::nlohmann_json"
find-package-name = "nlohmann_json" # only needed if installed using a package manager
```

## How it works

1. `camko` parses `camko.toml` from your project root.
2. It generates a `CMakeLists.txt` inside `.camko/`, translating each `camko.toml` section into the corresponding CMake set up: project definition, C++ standard, build type, tooling, (ccache, `compile_commands.json`), warnings, sanitizers, LTO, dependencies (via `FetchContent`), source globbing, test registration, and install rules.
3. CMake is invoked with `.camko` as the source root (`-S .camko`) and the build system from `build-system` as its generator (`Ninja` unless configured otherwise), so all paths to your actual  `src/`/`include/`/`tests/` directories are resolved one level up from there. Build output goes into `.camko/build/`, in a subdirectory named after the build system (`.camko/build/Ninja`, `.camko/build/Unix Makefiles`, ...), and changing `build-system` discards the caches of the previous build systems.
4. CMake performs the actual compilation, and camko simply reports the result.

` camko run` doesn't implement its own incremental build tracking - it always triggers a build step first and relies on CMake to determine whether anything has actually changed.

`camko test` follows the same pattern as `camko run`: it builds first, then invokes CTest. It does not check `[tests].enable-tests` before doing so, and it only knows about test files matching the `*_test.cpp` naming convention, built against Google Test.
